## 摘要

RAG Notebook 是一個面向企業內部知識工作的 AI 研究助理。使用者可以把文件整理成不同 notebook，針對選定來源提問，取得有引用依據的回答，並把有價值的回答、摘要、比較報告或會議整理保存成筆記。

它的核心價值不是「讓 AI 隨意回答」，而是讓 AI 在指定資料範圍內協助閱讀、比對、整理與產出初稿——**找得到依據就附上出處，找不到就明說**。對企業而言，這代表知識工作可以更快從大量文件進入可討論、可驗證、可追蹤的狀態。

產品可以完整部署在客戶自己的環境內：文件、索引、對話、稽核紀錄與評估結果都留在部署主機上，並可直接對接客戶既有的模型服務（自架開源模型或 Azure OpenAI）與企業身分系統（OIDC 或既有的 SSO 閘道）。

目前產品定位是單機部署的概念驗證，適合本機實驗、小型可信任環境、客戶內部試點與高價值流程驗證。若要直接面向大量使用者或公開網路，仍需要依照企業資安、治理與維運要求進一步產品化。

## 要解決的問題

企業內部常見的知識工作痛點包括：

- 文件很多，但人很難快速掌握重點、差異與矛盾。
- 問題通常跨多份文件，手動查找、摘錄與比對成本高。
- AI 回答若沒有來源依據，難以被研發、法遵、醫藥、客服或管理團隊信任；更糟的是 AI 在沒有依據時仍然「自信地」回答。
- 內部資料不一定能送出企業環境，導致一般雲端 AI 工具難以導入。
- 模型、檢索參數與文件格式會影響回答品質，但缺少可管理、可驗證的調校流程。

RAG Notebook 的設計目標，是把「文件、問題、答案、引用、筆記與評估」放在同一個可操作工作區裡，讓使用者既能提高效率，也能保留判斷依據。

## 產品概念

RAG Notebook 以 notebook 為主要工作單位。每個 notebook 可以包含一組來源文件、對話紀錄、釘選筆記與 AI 工具產出。

典型流程如下：

1. 使用者建立 notebook。
2. 上傳來源文件（Web URL 匯入仍在規劃中）。
3. 系統在背景抽取文字、建立分塊與索引，並回報每份文件的抽取品質。
4. 使用者針對文件提問，AI 回答時附上引用來源；找不到足夠依據時會明確表示。
5. 使用者點擊引用，回到原始來源片段檢查依據。
6. 使用者把重要回答、比較結果、會議整理或摘要保存成筆記，並可匯出。
7. 管理員透過 Eval Workbench 檢查檢索與回答品質，並調整設定。

這種設計把 AI 從「一次性聊天工具」轉成「可持續累積的研究工作區」。

## 主要能力

### 1. 有來源依據的問答

使用者可以選擇 notebook 內的來源並提問。系統會先從文件中找出相關片段（同時比對語意與關鍵字），再讓模型根據這些片段生成回答。

- **每個論點都可追溯**：回答附上引用編號，點擊後直接開啟來源並定位到被引用的那一段文字。
- **找不到依據時明確拒答**：若檢索到的片段相關度不足，或模型判斷資料中沒有答案，系統會回覆「找不到依據」，而不是硬擠出一個答案。
- **即時進度**：提問後畫面會依序顯示「檢索中」「生成中」等狀態，不必盯著空白畫面等待。
- **延伸提問**：每則回答後附上建議的追問；新 notebook 的對話區也會提供起始問題，幫助使用者開始探索文件。
- **可檢視檢索細節**：每則回答可展開查看實際找到了哪些片段與相關度分數，方便判斷回答品質。
- **對話管理**：可建立多段對話、重新命名、刪除，並把整段對話匯出為 Markdown。
- **一鍵回饋**：每則回答下方可評價「可以直接採用／方向對但不完整／不能用」，一次點擊即可；
  覺得有問題時可再選原因（找不到資料、答錯、引用對不上、資料裡沒有卻硬答、該拒答卻硬答等）。
  這些回饋提供給管理員作為改善依據，介面上也會明白告知使用者這一點。

適合情境：

- 查找研究報告中的關鍵結論。
- 詢問合約、規格、標準文件中的條款。
- 根據多份文件整理客戶、產品或專案背景。
- 快速確認某個答案是否有文件支持。

### 2. 多文件比較與整理（Studio 工具）

Studio 工具提供面向知識工作的常用產出。每個工具的結果都會先顯示給使用者確認，再由使用者決定是否存成筆記：

- **來源比較**：整理多份來源的「共同點」、「差異」與「待釐清」事項。
  - 不指定主題時，可一次比較 2–10 份來源（以各來源的摘要為基礎）。
  - 指定比較主題時，可比較 2–3 份來源；系統會先從每份來源分別檢索與主題相關的證據，再進行比較。
  - 結果附來源編號、檔名與證據狀態對照，存成筆記或匯出時一併保留；共同點會標明適用於哪些來源，避免把部分文件的共通內容誤認為全部文件一致。
  - 提示詞要求不把不同專案或版本的差異直接視為矛盾；證據不足時會標示需要確認的條件，不自動判定文件效力或取代關係，也不保證涵蓋全文所有差異。比較結論仍需人工核對。
- **Notebook 簡報**：以一段可展開的摘要，概覽整個 notebook 的來源內容。
- **會議記錄整理**：從逐字稿整理主題、決議、行動項目與未決事項。
- **學習指南、FAQ、時間軸**：把一組文件轉成更容易閱讀的概覽材料。
- **摘要翻譯**：將單一來源摘要翻譯成指定語言。
- **筆記與產出架**：重要回答、工具結果與手寫筆記集中在同一個產出架，依類型標示與篩選，可直接編輯，並可單篇或整批匯出為 Markdown。

這些功能降低了從「讀完文件」到「形成可討論材料」之間的轉換成本。

### 3. 來源管理與文件品質診斷

- **多種格式**：支援 PDF、Word、PowerPoint、Excel/CSV、HTML、純文字、Markdown 與字幕逐字稿（完整清單見「支援的資料格式」）。
- **背景處理**：上傳後在背景排隊抽取與索引，大型文件不會拖慢其他使用者；處理失敗會自動重試，服務重啟也不會遺失排隊中的工作。畫面上即時顯示每份來源的處理狀態。
- **抽取品質診斷**：每份來源都會留下診斷資訊——抽出多少文字、切成幾段、用了哪種解析方式、有哪些警告、在哪個階段失敗——並提供內容預覽。這讓使用者能分辨問題出在「文件沒被正確讀進來」，還是「檢索／回答不夠好」。
- **試算表的特殊處理**：問答形式的表格會被辨識為一題一答；其他表格以資料列為單位建立索引。
- **全域搜尋**：跨所有 notebook 搜尋 notebook 名稱、來源檔名與摘要、對話標題與筆記。
- **重新索引與刪除**：可對單一來源重新處理或刪除。

### 4. 領域知識設定：讓系統聽得懂你的行話

企業文件常充滿內部代號、縮寫與專有名詞，而且各部門對回答方式有自己的規則。Notebook 擁有者可以為每個 notebook 設定：

- **領域提示（domain hints）**：術語、同義詞、定義與查詢擴充。例如讓系統知道「PM」在這個 notebook 指的是「粒狀物」而不是「專案經理」。這些提示只在檢索時用來擴充查詢，不需要重新建立索引，也不會增加額外的模型呼叫。
- **回答規則（answer policy）**：約束回答的方式，例如語氣、格式或必須附加的提醒。

兩者都有數量與長度上限，且**不能取代來源證據，也不能放寬系統的引用規則**——它們是給 AI 的工作指引，不是額外的知識來源。

另外，系統內建一條試算表保護規則：試算表來源適合查找特定資料列與語意搜尋，但**不適合做精確的計數、加總或排名**。遇到這類問題時，回答會加註提醒，而不是給出一個看似精確、實則不可靠的數字。

### 5. Eval Workbench：把回答品質變成可討論的指標

RAG 系統的品質通常不只取決於模型，也取決於文件抽取、分塊、檢索、reranking、語言、領域詞彙與回答規則。RAG Notebook 內建管理員 Eval Workbench，讓團隊可以**在部署環境內**建立題集、執行評估、比較不同設定，並保留歷史結果——客戶資料不需要離開環境。

這對企業導入很重要，因為它讓「回答品質不好」不再只是主觀感受，而可以拆成：

- 是否找到了正確文件片段？
- 正確片段排名是否足夠前面？
- 是否因為信心門檻、語言或關鍵字而漏找？
- 調整參數後是否真的改善？

主要功能：

- **題集建立**：管理員可手動出題，也可由 AI 從已索引的文件產生候選題目（含可回答、跨語言、應拒答等題型）；**候選題目必須經人工審核才會成為正式題目**。
- **檢索評估**：以 Recall、MRR 等指標衡量是否找到正確片段，並可並排比較兩次執行結果。
- **回答品質評分（選用）**：可額外開啟回答正確性、是否有依據、引用是否正確、拒答是否恰當等評分。這些分數與檢索指標分開呈現，作為參考訊號而非絕對標準；沒有參考答案的題目，正確性評分會標示為不適用。
- **設定實驗與套用**：可建立多組檢索設定（retrieval profile），用同一份題集比較後，套用較佳的設定，也可隨時切回。需要重新建立索引的設定不會被默默套用。
- **領域設定比較**：以「不使用／只用領域提示／只用回答規則／兩者都用」四種模式比較同一份題集，確認領域設定真的有幫助。
- **調參指南**：內建說明頁，依「症狀 → 可能原因 → 建議調整」協助管理員判斷該調參數還是該修題目。
- **匯出**：去識別化的設定與報告可安全對外分享；包含題目與答案的完整內部報告需明確確認，並以高敏感度事件記入稽核紀錄。

**回饋作為題目的來源**：使用者在日常使用中留下的評價與原因，會集中在管理員的「回饋」頁，
可依評價、原因、notebook 與時間篩選，用來找出最常失敗的問題類型。要特別說明的是，
**這些數字不是品質指標**——每則回饋來自不同的問題、時間與使用者期待，屬於不受控的樣本，
不能用來證明某項調整有效；驗證調整仍須以固定題集比較。回饋的價值在於指出問題集中在哪裡，
以及提供建立題集的素材。

真正的客戶品質基準，仍需在客戶環境內建立經核准的代表性題集。

### 6. 企業身分整合與帳號安全

- **OIDC 單一登入**：可對接 Microsoft Entra ID、ADFS、Keycloak 等支援 OIDC 的身分平台。
- **Windows 帳號自動登入**：透過客戶既有的反向代理或 SSO 閘道完成 Windows 驗證，再把已驗證身分交給本系統；系統以共享密鑰（並可加上來源 IP 限制）確認身分確實來自受信任的閘道。
- **群組對應管理員權限**：可指定哪些企業群組的成員自動取得管理員權限。
- **保留緊急本機登入**：SSO 故障時，本機管理員帳號仍可登入處理（可依政策關閉）。
- **身分整合健檢頁**：管理員可檢視目前啟用的登入方式、設定是否完整，以及登入失敗的原因代碼。
- **帳號安全**：首次部署的管理員帳號必須在第一次登入時變更密碼；登入失敗次數過多會暫時鎖定；登入狀態最長 12 小時（可調整）即需重新登入，變更密碼會讓該帳號在其他裝置上的登入全部失效。

SSO 功能預設關閉，依客戶環境逐項啟用。SAML 目前尚未支援，依客戶需求再評估。

### 7. 模型連線與部署彈性

- **使用客戶自己的模型**：支援 Azure OpenAI，以及任何 OpenAI 相容介面的服務，包括以 vLLM、Ollama、TEI 自架的開源模型。本機或內網服務可不設 API key。
- **對話模型與向量模型可分開設定**：兩者可以來自不同的服務，例如對話用一台 GPU 主機上的開源模型，向量用另一台主機上的 multilingual-e5。
- **連線診斷**：管理員可分別測試對話與向量模型，查看延遲、向量維度，並偵測模型支援哪些參數與能力（串流、用量回報、JSON 格式、推理強度、圖片理解等）。
- **自動適應新型模型**：部分新一代推理模型不接受傳統的 temperature 等參數。系統會依實際測試結果決定送出哪些參數，而不是從模型名稱猜測，避免換模型後整個系統無法運作。
- **更換向量模型不必全部重來**：換成不同維度的向量模型時，系統提供專門的遷移流程，保留仍可沿用的向量，只把需要的來源標記為重新索引。

### 8. 使用體驗

- 繁體中文介面，中文輸入法友善。
- 淺色、深色或跟隨系統的顯示主題。
- 支援平板與手機寬度，窄螢幕可在「來源／對話／工作台」之間切換。
- 鍵盤操作、螢幕閱讀器標籤與減少動態效果等無障礙設計。
- 錯誤時顯示使用者看得懂的訊息，技術細節只留在系統紀錄中。

## 目前版本的限制

以下是導入前應讓使用者與決策者知道的限制。大部分已列入路線圖（見文末）；知道限制，才能正確設定期待與選擇試點情境。

**內容涵蓋範圍**

- **來源摘要只取自文件前段。** 每份來源的 2–4 句摘要目前依文件開頭約前幾頁產生。以摘要為基礎的功能——notebook 簡報、未指定主題的來源比較、學習指南、FAQ、時間軸、摘要翻譯——因此反映的是各文件的開頭，而非全文；長篇報告若開頭沒有摘要章節，結果可能偏向封面、目錄與前言。需要全文細節時，請改用有引用的問答，或指定主題的來源比較（會先從各來源檢索證據）。
- **會議記錄只讀取逐字稿前段。** 目前最多讀取約 16,000 字，較長的會議後段（通常是決議所在）不會被納入，且畫面上尚未提示涵蓋範圍。
- **WebVTT 逐字稿的講者標籤目前會被移除**，因此會議記錄與問答無法依講者區分發言。
- **逐字稿與 Word 文件的引用位置較粗略**：系統內點擊引用仍可定位到確切段落，但匯出的文件中，引用位置只會顯示為「逐字稿」或「文件」，而非時間點或章節。

**語言與檢索**

- **跨語言提問效果較弱。** 以中文提問、但來源是英文（或反之）時，系統仍能透過語意比對找到內容，但關鍵字比對無法跨語言，相關度也偏低，可能找到較少片段或觸發拒答。混合語言的 notebook 建議以來源的語言提問。
- **介面目前只有繁體中文**；英文介面與個人語言設定已在規劃中。

**資料格式**

- **掃描檔 PDF 與圖片無法抽出文字**（需要 OCR，規劃中）；這類文件上傳後會在診斷中顯示抽不到內容。
- **舊版 Office 格式（.doc、.ppt、.xls）不支援**，需先另存為新版格式。
- **PowerPoint 只讀文字**：標題、內文、表格與備忘稿會被索引，圖片與圖表內容不會。
- **試算表不適合做精確統計**：可查找資料列與語意搜尋，但計數、加總、排名需使用專門的分析工具。
- **上傳大小**：單次最多 5 個檔案；每個檔案上限 50 MB，Excel、PowerPoint、CSV 為 20 MB（管理員可調整）。

**協作與權限**

- **Notebook 目前只有擁有者本人能使用**，尚不支援分享 notebook 或分享單篇產出給同事；需要交付時請使用 Markdown 匯出。
- **畫面上的時間以 UTC 顯示**，尚未轉換為使用者所在時區。

## 企業價值

### 提升知識工作效率

RAG Notebook 可以縮短閱讀、搜尋、整理、比較與初稿產出的時間。使用者不需要在多份文件、搜尋結果、筆記工具與聊天工具之間反覆切換。

### 強化回答可驗證性

引用來源與來源片段定位讓使用者可以快速回到原始依據；找不到依據時明確拒答，避免使用者被看似合理的錯誤答案誤導。這對法遵、研發、醫藥、客服知識庫、合約審閱與管理決策尤其重要。

### 支援資料留在客戶環境

產品可搭配客戶既有的自架模型或 Azure OpenAI endpoint。資料、索引、稽核與評估結果都保留在部署環境內，品質評估也在環境內完成，降低資料外流與資料主權疑慮。

### 讓 AI 導入可治理

管理員可以檢查模型連線、查看稽核紀錄、追蹤用量與安全事件，並透過 Eval Workbench 驗證調整是否有效。這讓 AI 從個人試用工具逐步走向可管理的企業能力。

## 治理與資料邊界

RAG Notebook 的治理原則是：必要資料留在正確位置，治理紀錄避免複製敏感內容。

目前設計重點包括：

- **資料隔離**：每位使用者只能存取自己的 notebook 與其中的來源、對話與筆記。
- **金鑰保護**：模型服務的 API key 加密保存，不會回傳到瀏覽器。
- **稽核紀錄**：使用者管理、模型設定變更、索引重建、評估設定套用、各類匯出等重要操作都會記錄；可能把內容帶出環境的匯出（完整評估報告、對話與筆記匯出）標記為高敏感度。
- **用量與安全事件紀錄**：每次模型呼叫的用途、延遲與 token 用量都會記錄（服務未回報用量時會標示為估算值）；疑似提示注入（含中文句型）、隱藏字元、疑似密鑰等輸入會被記錄為安全事件，目前為警示記錄，不會阻擋使用者。
- **紀錄不複製內容**：稽核與治理紀錄只保存操作類型、對象編號與精簡摘要，預設不複製原始提問、來源全文、檢索片段、模型輸出或 API key。
- **基本 Web 防護**：所有變更資料的操作都有跨站請求偽造（CSRF）防護；上傳檔案在寫入前即檢查大小；AI 產生的內容在顯示前經過安全過濾。

這些設計能支援內部試點與治理討論，但不等同於已完成所有企業級資安認證。若要正式上線，仍應依客戶資安政策進行額外審查。

## 部署與整合模式

目前產品適合以下部署模式：

- 本機或單機測試。
- 小型可信任內部環境。
- 客戶環境內的 PoC 或 pilot。
- 搭配客戶既有 LLM/embedding endpoint 的封閉式部署。

部署方式：

- **單機部署**：以 Docker Compose 啟動網站服務與獨立的背景處理服務；所有資料集中在一個資料夾，備份只需封存該資料夾。
- **放在企業反向代理之後**：由反向代理負責 HTTPS、對外入口與來源 IP 限流；SSO 閘道可在同一層完成 Windows 驗證。
- **可維運性**：提供健康檢查端點供監控使用；畫面頁尾與系統紀錄都會顯示版本號與程式版本，問題回報可直接對應到確切版本。

目前不建議直接作為公開網際網路服務使用。若要正式產品化，仍建議補強：

- 依客戶需求補齊 SAML、IdP 登出連動等身分整合，以及 notebook 分享等更細緻的權限模型。
- 更完整的治理 dashboard 與報表匯出。
- 更成熟的 LLM 設定管理與多 profile 切換。
- 部署監控、備份、復原與容量規劃。
- 依客戶政策完成資安測試與稽核。

## 支援的資料格式

目前支援：

- PDF（含文字層的 PDF；掃描檔需 OCR，尚未支援）
- Word（.docx）
- PowerPoint（.pptx，只讀文字：標題、內文、表格、備忘稿）
- Excel（.xlsx）與 CSV（問答表會被辨識，其他表格以資料列分塊）
- HTML
- 純文字（.txt）與 Markdown
- SRT／VTT 字幕逐字稿

所有支援格式都會留下抽取品質診斷，讓使用者能區分「抽取失敗」與「檢索／回答失敗」。

規劃中的格式與能力：

- Web URL 匯入，需具備 SSRF 防護與客戶 egress policy 控制。
- OCR 與圖片理解，依客戶需求與模型能力逐步加入；圖片上傳會以模型是否通過圖片理解檢測為前提。
- 文件章節結構辨識，讓引用位置與比較可以依章節進行。
- 試算表的精確 filtering/counting/aggregation，另以受限制的 table-query workflow 處理，不把 top-k RAG 當成完整資料分析工具。

## 適合的使用情境

- 研究報告閱讀與跨文件整理。
- 產品、法規、醫藥、技術文件問答。
- 客戶專案背景整理。
- 會議逐字稿轉會議記錄（長會議目前只涵蓋前段，見「目前版本的限制」）。
- 內部 FAQ 與知識庫初稿建立。
- 多份文件的共同點、差異與待釐清事項整理。
- 模型/檢索品質的內部評估與調校。

## 不適合直接承諾的情境

目前版本不應被定位為：

- 取代正式文件管理系統。
- 取代資料倉儲、BI 或 SQL 分析系統。
- 取代人工審閱、法遵簽核或醫療判斷。
- 多人共同編輯同一份 notebook 的協作平台。
- 可直接公開上線的 SaaS 產品。
- 不需評估即可保證回答完全正確的 AI 系統。

它更適合作為企業內部 AI knowledge workflow 的 PoC/pilot 基礎，透過真實文件與評估流程逐步驗證價值。

## 導入建議

### Phase 0：導入前確認

- 以非技術人員也能回答的問法，確認使用人數、可接受的回答速度、資料更新頻率、權限與資安要求、驗收方式與預算。
- 取 2–3 份去識別化的真實樣本上傳試跑，查看抽取品質診斷：文字是否完整、有無警告、逐字稿的講者與時間資訊是否保留。
- 請客戶提出「他們自己會問的題目＋正確答案」，作為日後驗收用的題集。

### Phase 1：PoC 驗證

- 選定 1 到 2 個高價值使用情境。
- 準備代表性文件集。
- 設定客戶 LLM/embedding endpoint，並用連線診斷確認能力。
- 建立 notebook，測試問答、引用、比較、摘要與筆記流程。
- 收集使用者對回答品質、引用可信度與工作效率的回饋。

### Phase 2：品質與治理

- 用 Eval Workbench 建立代表性題集。
- 比較不同 retrieval profile 的效果。
- 以「不使用／領域提示／回答規則／兩者都用」模式比較 domain 設定，必要時開啟回答品質評分；參考答案不足時不得把評分當作絕對標準。
- 檢查稽核紀錄、用量紀錄與安全事件紀錄是否符合治理需求。
- 明確定義哪些問題適合回答、哪些情境應該拒答。

### Phase 3：擴充資料來源與工作流

- 依需求加入 Web URL、OCR、圖片理解與結構化表格查詢等能力。
- 在客戶環境以核准的題集驗證既有 domain hints 與 answer policy，避免把自動產生的草稿當成客戶的標準答案。
- 依需求加入 notebook 或產出分享。
- 針對高頻工作流設計更完整的 artifact/report 產出流程。

## 衡量成功的指標

建議以以下指標評估 PoC 是否值得進一步產品化：

- 使用者完成閱讀/整理任務的時間是否下降。
- 回答是否能穩定附上正確引用；沒有依據時是否正確拒答。
- 使用者是否願意把回答或工具產出保存成筆記。
- 題集的檢索指標是否改善。
- 管理員是否能理解並操作 LLM 設定、索引狀態與評估結果。
- 資料留存、稽核與部署方式是否符合客戶內部政策。

## 路線圖重點

近期建議優先方向：

1. **會議逐字稿試點準備**：讓會議記錄涵蓋完整逐字稿並提示涵蓋範圍、保留 WebVTT 講者標籤、讓逐字稿與 Word 文件的引用位置顯示時間區間或章節，並讓來源摘要取樣整份文件而非只看開頭。
2. **Customer Eval Set**：在資料不離開客戶環境的前提下，建立經核准且含必要參考答案的代表性題集，形成可重複的品質基準。
3. **E2 validation**：用相同題集比較「不使用／領域提示／回答規則／兩者都用」，確認 domain 設定提升品質且不增加誤判或資料外洩。
4. **分享與協作（依客戶需求啟動）**：已完成規模評估，尚未排程。第一步是把單篇產出唯讀分享給指定同事，其次才是唯讀的 notebook 成員。
5. **Admin LLM operations**：在已完成的連線診斷基礎上，加入多組模型設定管理與安全切換。
6. **Source-format next step**：加入具 SSRF 防護與 egress policy 控制的 Web URL 匯入；文件章節結構、OCR 與圖片理解依實際語料與模型能力評估。
7. **Governance**：依需求補上彙總 dashboard、報表匯出與保存期限政策；SAML、英文介面、音訊轉錄與語音摘要維持依客戶需求投入。

## 結語

RAG Notebook 的定位，是讓企業把內部文件轉成可提問、可引用、可整理、可評估的 AI 工作區。它不是單純的聊天介面，而是一個結合文件管理、檢索、生成、筆記、評估與治理的知識工作流程雛形。

對客戶而言，最適合的導入方式是從明確場景開始，用真實文件驗證效率與可信度，再逐步擴充格式、治理與正式部署能力。
