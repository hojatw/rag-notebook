# 部署環境脈絡

`PERFORMANCE.md`、`QUALITY.md`、`ROADMAP.md` 裡大量的取捨——為什麼延後 FTS5、
為什麼不做 agentic 樹狀檢索、為什麼所有適配都必須在應用程式端——都是從這裡的
幾個事實推導出來的。這份文件把那些事實寫進 repo，讓接手的人看得到取捨的依據，
而不是只看到結論。

> **這是「由來」，不是「規格」。** 本專案已在不只一個客戶環境被使用，各自的模型、
> 硬體與使用規模都不同。下面描述的是**專案初期做 POC 時所面對的環境**，
> 它形塑了既有的設計取捨；它**不是**產品的部署需求，也不代表未來的部署會長這樣。
> 讀 backlog 裡的判斷時，請把它當成「當初是在什麼條件下做的決定」。

> **刻意去識別化。** 客戶名稱、機房、實際硬體型號等資訊不寫進 repo；需要那些細節時
> 看本機的 `local/handover.md`（gitignored）。這裡只保留**會影響工程判斷**的事實。

## 塑造了現有設計的幾個事實

### 1. 推論端不可改

初期環境的 chat 與 embedding 服務是**借用**既有的共用資源，不歸專案控制：
無法換模型、無法調整 serving 參數、無法要求擴充。

**這是影響最深的一條。** 它的直接後果是：**任何調整都只能在應用程式端做**。
所以 backlog 裡看不到「換一個更適合的 embedding 模型」這類選項——那從來不在
可選集合裡。e5 的 `query:` / `passage:` prefix 做成應用程式端的設定
（`QUALITY.md` `Q0-1`）就是這個限制的產物。

### 2. 模型組合：~30B 級開源 chat + 1024 維多語 embedding

具體是 Gemma 4 31B 與 multilingual-e5-large。這兩個名字在 backlog 裡到處出現，
因為它們決定了幾件很具體的事：

- **1024 維** —— 與更早期使用的 1536 維模型不同。維度變更不是換個設定就好，
  Chroma 會在第一次寫入時鎖定集合寬度，這是整個 `O0` 遷移流程存在的原因
  （見 [`DEVELOPMENT.md`](DEVELOPMENT.md) → *Changing the embedding dimension*）。
- **e5 需要 prefix** —— 不加 `query:` / `passage:` 會明顯變差，而這只能在呼叫端補。
- **512 token 輸入窗** —— 中文約 1 字 1 token，所以分塊大小的上限是真實約束，
  不是理論值（`QUALITY.md` `Q0-5`）。
- **共用且會被限流** —— LLM 呼叫必須有重試與退避（`PERFORMANCE.md` `P0-3`），
  而**延遲是最大的感知成本**：目前每個問題 3 次序列 LLM 呼叫已經是主要瓶頸
  （`P3-2`）。任何會增加序列呼叫次數的設計都要先過這一關——
  `QUALITY.md` `Q1-7` 之所以不照 PageIndex 原本的 LLM 樹狀導航實作，就是這個理由。

### 3. 使用規模：約 200 名具名使用者，非同時在線

單機部署。這個數字大到不能忽視並行（所以 briefing 鎖必須跨行程、攝取要有佇列），
但小到不需要水平擴展或外部服務（所以 SQLite + 本機檔案 + 嵌入式 Chroma 是合適的，
Redis 被明確延後——見 `PERFORMANCE.md` `P1-1`）。

**「右尺寸」的判準就來自這裡**：會影響 200 人的問題要修，只有在 10 萬人規模才會出現的
問題記錄下來並附重啟條件。

### 4. 語料：幾百頁的研究報告，加上廠商自建文件

兩個特性各自帶來不同的工程後果：

- **長文件** —— 幾百頁的 PDF 讓抽取成為 CPU 密集工作，這是攝取必須離開網頁行程的
  原因（`P1-1`）。也讓文件結構成為有價值的檢索訊號（`ROADMAP.md` `A12`）。
- **結構不可預測** —— 廠商自建的文件沒有一致的排版慣例。因此任何依賴文件結構的功能，
  **「偵測不到時安全退回現況」必須是主要路徑，不是邊緣案例**
  （`A12` 實測顯示約四分之一的樣本沒有任何可用的結構訊號）。

### 5. 語言：繁體中文為主，混合英文內容

不是「支援多語言」那種抽象需求，而是幾件具體的事：中文約 1 字 1 token（不是英文的
4 字元 1 token，估算成本時差 4 倍）；`LIKE` 之外的關鍵字檢索需要 CJK 斷詞，
這正是 FTS5 遲遲無法直接套用的原因（`P1-2` / `Q1-2`）；跨語言檢索（中文問題、
英文語料）是真實情境而非測試案例（`Q1-4`）。

### 補充（2026-09-17）：推論端是兩台可切換，不是一台固定

依本文件開頭的規定，這裡是補一段而不是改寫上面的第 1、2 條。

**由專案負責人確認的事實**：chat 有兩台主機——**Gemma 4 31B 在新機器上，
gpt-oss-120b 在舊機器上**。2026-09 新機器進維修，該期間部署暫時改用舊機器的
gpt-oss-120b。embedding（multilingual-e5-large）從頭到尾沒有變動。

**仍然成立的**：第 1 條「推論端不可改」沒有失效——仍然無法調整 serving 參數或
要求擴充，所有調整仍然只能在應用程式端做。

**需要修正的**：「**固定**」這個字不成立。實際是兩台、會切換，而且**切換是常態
運作而非意外**。`PERFORMANCE.md` 與 `QUALITY.md` 開頭都把 serving side 描述為
`borrowed and fixed`，其中「borrowed」正確、「fixed」不正確。

**已經因此修正的程式行為**：能力探測先前由一個涵蓋兩條連線的識別碼決定有效範圍，
於是每切換一次 chat 主機，就會作廢 embedding 那邊剛測得的輸入視窗——fail-closed
所以不會壞，但會靜默退回設定值。已改為每條連線各自一個識別碼。

**還沒重新評估的**：`PERFORMANCE.md` 與 `QUALITY.md` 中引用「serving side is fixed」
的項目，需要逐條確認「固定」這個前提對該項取捨是否具有承重作用。**這是待辦，不是
已完成的判斷**——本次只確認了事實，沒有逐條重評。

### 補充（2026-09-19）：上面那項待辦已完成

上一段結尾列為待辦的逐條重評做完了。**結論：33 條裡只有 6 條的取捨真正依賴「固定」
這個前提**，其中 5 條是同一個模式——把驗證對象寫死成模型名字。4 條是措辭綁定了單一
主機但取捨不變，其餘 23 條不受影響。逐條結果寫在各條目自己的文字裡，不集中在這裡。

**兩項與原先假設相反的發現，記下來免得再推一次：**

1. **拒答門檻讀到的不是 embedding 餘弦值。** `QUALITY.md` `Q0-2` 原文說門檻依賴
   e5 的分數分布。實際上 `retrieve()` 回傳的是 `rerank_chunks` 覆寫過的
   `combined = rerank_weight·rerank_score + rerank_base_weight·hybrid_score`，而
   `rerank_weight` 預設 0.8——門檻比對的數值有八成來自 **chat** 模型。所以這條是
   「固定」前提下最承重的一項，而不是原先判斷的「不受影響」。
2. **Eval 比較頁的模型差異提示，大部分在 O5c 就做好了。** 比較頁已經逐欄 diff
   `llm_snapshot` 並標示變動列。（我一度以為缺的是「那張表排在指標表下方」——**那是錯的**，
   它排在指標表上方。）真正缺的是**顯著性**：換模型那一列的長相，和它正上方參數表裡
   「換了一個參數」完全一樣，而後者正是比較功能存在的目的。因此 `ROADMAP.md` `E1g`
   是一個版面修正，不是新功能。

**新確認的事實（由專案負責人確認）**：**兩台 chat 主機與 e5 embedding 端點都不需要
API 金鑰**。先前 `PERFORMANCE.md` `P2-6` 把「無金鑰」寫成 Gemma 的屬性；正確的說法是
**每條連線各自的屬性**，而目前三條連線都無金鑰。

**產出的新工作項**：`QUALITY.md` `Q0-7`（把 `Q0-3`／`Q0-4` 與 abstain marker 遵從性
合併成綁在連線指紋上的一致性檢查）與 `ROADMAP.md` `E1g`。

## 這份文件不涵蓋的

- **具體的客戶、硬體、網路拓撲** —— 見本機 `local/handover.md`。
- **每個部署的認證方式** —— 見 [`AUTHENTICATION.md`](AUTHENTICATION.md) 與
  [`SSO_DEPLOYMENT.zh-TW.md`](SSO_DEPLOYMENT.zh-TW.md)。
- **實際的效能數字** —— 沒有量過的就不寫。目前只有零星實測散在各 backlog 條目裡，
  並且都標明了樣本來源與限制。

## 這些事實改變時

它們是判斷的**依據**，不是背景裝飾。如果某個部署的條件明顯不同——推論端可控、
使用規模差一個數量級、語料換成短文件——那 backlog 裡引用這些事實的取捨就該重新評估，
而不是照抄。真的發生時，請在這裡補一段而不是改寫既有內容：**知道「當初為什麼那樣決定」
和知道「現在的條件是什麼」一樣重要。**

## 「這還是 POC 嗎？」

這份文件描述的規模與限制，正是判斷這個問題的依據。**判準本身寫在
[`SECURITY.md`](SECURITY.md) → *What "proof of concept" is actually claiming***：
三個可驗證的條件（`SEC-4` 關閉、`Q1-3` eval set 存在、有第二個人照文件完成過一次升級），
而不是感覺。

需要在這裡強調的一點：**單機架構本身不是「還沒長大」。** 在約 200 人、非同時在線的
規模下，SQLite + 本機檔案 + 嵌入式 Chroma 是相稱的選擇，而不是暫時的替代品。
如果哪天要重新評估這個定位，該檢討的是加固與**可量測性**，不是把架構換掉。
